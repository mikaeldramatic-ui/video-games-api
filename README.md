# 🎮 Video Games API

A REST API for video games, built with **AWS Lambda**, **API Gateway** and the **Serverless Framework**.

> **School project.** This API is part of the course *Apputveckling i molnet* (Cloud App Development), week 44, week 2 of 6. The assignment was to build our own REST API with a theme of our choice, after first building a Shakespearean Insults API step by step. I chose video games, with my own favourite games as seed data.

## Tech stack

| Tool | Used for |
|---|---|
| **AWS Lambda** | One function per endpoint |
| **API Gateway (HTTP API)** | Receives HTTP requests and routes them to the right Lambda function |
| **Serverless Framework v4** | Creates the Lambda functions and API Gateway from `serverless.yml` |
| **Node.js 24** (arm64) | Runtime for the Lambda functions |
| **Middy** | Middleware for parsing the request body and handling errors |
| **Insomnia** | Testing all endpoints |
| **Git & GitHub** | One branch per step, merged through pull requests |

Region: `eu-north-1` (Stockholm)

## Data model

A game looks like this:

```json
{
  "id": 2,
  "title": "The Legend of Zelda: Breath of the Wild",
  "developer": "Nintendo",
  "platform": "Nintendo Switch",
  "genre": "Action-adventure",
  "year": 2017,
  "rating": 10
}
```

| Field | Type | Description |
|---|---|---|
| `id` | number | Generated by the API, cannot be set by the user |
| `title` | string | Name of the game |
| `developer` | string | The studio that made the game |
| `platform` | string | One or more platforms, e.g. `"PC, Playstation 5"` |
| `genre` | string | Genre |
| `year` | number | Release year |
| `rating` | number | My own rating, 1–10 |

**Seed data:** Subnautica, The Legend of Zelda: Breath of the Wild, The Callisto Protocol, Gotham Knights, Lightyear Frontier and Assassin's Creed II.

## Endpoints

| Method | Endpoint | Description | Success |
|---|---|---|---|
| `GET` | `/games` | Get all games | 200 |
| `GET` | `/games?platform=pc` | Filter by platform | 200 |
| `GET` | `/games?genre=survival` | Filter by genre | 200 |
| `GET` | `/games/{id}` | Get one game | 200 |
| `POST` | `/games` | Add a game | 201 |
| `PUT` | `/games/{id}` | Replace a whole game | 200 |
| `PATCH` | `/games/{id}` | Update one or more fields | 200 |
| `DELETE` | `/games/{id}` | Delete a game | 200 |

### Query parameters on `GET /games`

- `platform` and `genre` match **part of the text** and are **case-insensitive**. `?platform=pc` matches both `"PC"` and `"PC, Playstation 5"`.
- The parameters can be **combined**. A game then has to match both:

```http
GET /games?platform=pc&genre=survival
```

### `POST /games` and `PUT /games/{id}`

All six fields are required, with the right types. `title`, `developer`, `platform` and `genre` must be text, `year` and `rating` must be numbers, and `rating` must be between 1 and 10:

```json
{
  "title": "Hades",
  "developer": "Supergiant Games",
  "platform": "PC",
  "genre": "Roguelike",
  "year": 2020,
  "rating": 9
}
```

If something is wrong, the error message lists exactly which fields need fixing:

```text
400 Bad Request
Missing or invalid fields: year, rating.
```

### `PATCH /games/{id}`

Only the fields that should change are sent. Everything else is kept:

```json
{
  "rating": 10
}
```

## Status codes

| Code | Meaning | When? |
|---|---|---|
| **200** OK | Successful request | GET, PUT, PATCH, DELETE |
| **201** Created | Something new was created | POST |
| **400** Bad Request | Missing fields, wrong type, or rating outside 1–10 | POST, PUT |
| **400** Bad Request | Empty body | PATCH |
| **404** Not Found | No game with that id | GET, PUT, PATCH, DELETE with `{id}` |
| **415** Unsupported Media Type | No JSON body was sent | POST, PUT, PATCH (from Middy) |
| **422** Unprocessable Entity | The body is not valid JSON | POST, PUT, PATCH (from Middy) |

## How we built it, step by step

Each step was built on its own **feature branch**, tested in Insomnia and merged into `main` through a pull request.

### Step 1 – Project setup and seed data
A new Serverless Framework project with the same structure as the Shakespearean Insults API: `data/`, `functions/` and `responses/`. The seed data lives in `data/games.mjs`, and `sendResponse()` in `responses/index.mjs` makes every function respond the same way.

### Step 2 – `GET /games`, get all games
The first function returns the whole list. The `httpApi` event in `serverless.yml` makes Serverless create an API Gateway with one shared base URL for all endpoints.

### Step 3 – `GET /games/{id}`, path parameter
The id is read from `event.pathParameters.id`. It arrives as a **string**, so it is converted with `Number()` before comparing with `.find()`. If no game is found, the API responds with **404**.

### Step 4 – `POST /games`, request body
The body arrives as a JSON string and is parsed with `JSON.parse()` inside a `try/catch`, so invalid JSON returns **400** instead of crashing. All six fields are validated. The new id is the highest existing id plus 1, and the response is **201 Created**.

### Step 5 – `DELETE /games/{id}`
`findIndex()` returns the game's **position** in the array, or `-1` if it doesn't exist. The game is removed with `splice()`, and the response includes the deleted game.

### Step 6 – `PUT /games/{id}`, replace
Combines a path parameter and a body. The game at that position is replaced with `games[index] = updatedGame`, keeping the id from the URL. The response is **200**, since nothing new was created.

### Step 7 – Query parameters
`GET /games` was extended with filtering through `event.queryStringParameters`. `|| {}` keeps requests without parameters from crashing. Both the search value and the field are lowercased, and `.includes()` is used since a game can have several platforms.

### Step 8 – Middy 🔧

The final step was to simplify error handling with **Middy**, a middleware library for Lambda.

**Middleware** is code that runs before and/or after the function itself and takes care of things that are the same across many functions:

```text
Request → httpJsonBodyParser → our function → httpErrorHandler → Response
```

Installed packages:

```bash
npm install @middy/core @middy/http-json-body-parser @middy/http-error-handler @middy/util
```

**8a – `createGame` and `updateGame` were rebuilt with Middy**

- `httpJsonBodyParser()` parses the body **before** the function runs. The `try/catch` around `JSON.parse()` is no longer needed, and `event.body` is already an object.
- Errors are **thrown** with `createError()` instead of returned:
  ```js
  throw createError(404, 'Game not found.');
  ```
- `httpErrorHandler()` catches the errors and turns them into HTTP responses with the right status code.
- The function is wrapped with `middy()` but is still exported as `handler`, so `serverless.yml` didn't need to change:
  ```js
  export const handler = middy(updateGame)
      .use(httpJsonBodyParser())
      .use(httpErrorHandler());
  ```

**8b – `PATCH /games/{id}` was built with Middy from the start**

PATCH differs from PUT in that only the fields that are sent get updated. The existing game and the changes are merged with the **spread operator**:

```js
const updatedGame = { ...games[index], ...body, id: id };
```

1. `...games[index]` copies all existing fields.
2. `...body` overwrites the fields that were sent.
3. `id: id` comes last, so the id always comes from the URL.

**Result:** each handler only contains what is unique to that endpoint, while body parsing and error handling are taken care of in one place by Middy.

**8c – Better validation after code review**

During code review, a classmate pointed out that `createGame` only checked that the fields *existed*, not that they had the right *type*. A request with `"title": 123` was accepted. `createGame` and `updateGame` now validate types with `typeof`, which also catches missing fields, since a missing field is `undefined`. The invalid fields are collected with `.filter()`, so the error message tells the user exactly which fields to fix:

```js
const textFields = ['title', 'developer', 'platform', 'genre'];
const numberFields = ['year', 'rating'];

const invalidText = textFields.filter((field) => typeof body[field] !== 'string');
const invalidNumbers = numberFields.filter((field) => typeof body[field] !== 'number');
```

## Limitations

The API has **no persistent storage**. Every Lambda function has its **own copy** of the array in `data/games.mjs`, so a game created with `POST` will not show up in `GET /games`. Changes can also disappear when Lambda starts a new container.

This was an intentional part of the assignment, to keep the focus on API Gateway and Lambda. The next step in the course is connecting the API to **DynamoDB**.

## Getting started

1. Clone the repo and install the packages:
   ```bash
   npm install
   ```
2. Create a `config.yml` in the project root with the ARN of an IAM role for Lambda:
   ```yaml
   role: arn:aws:iam::<ACCOUNT-ID>:role/<ROLE-NAME>
   ```
3. Deploy:
   ```bash
   sls deploy
   ```
4. Use the base URL printed in the terminal and test the endpoints in Insomnia or Postman.
